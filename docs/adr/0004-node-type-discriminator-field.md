# `Node` subclasses carry an explicit `type` discriminator field

`StartNode`, `EndNode`, `Step`, and `Decision` each add a `type: Literal[...]` field (`"start"`, `"end"`, `"step"`, `"decision"`), and `Flowchart.nodes` is typed as a Pydantic discriminated union on that field rather than plain `list[Node]`. Without it, deserializing a `Flowchart` from JSON — which is how `002_text_parsing_chain` receives the LLM's structured output, since the LLM can only emit text, not construct Python objects directly — has no way to tell which subclass a given node dict should become: nothing in `{"id": "start", "label": "Start"}` says "I'm a `StartNode`," so Pydantic falls back to the declared field type and every node collapses to plain `Node`, which then fails `Flowchart`'s own start/end validators. Direct Python construction (`StartNode(id=..., label=...)`, as in `001`'s tests) was unaffected by this gap — it only surfaces on the JSON round-trip a real parsing chain requires. The discriminator also gets included in the JSON Schema `Flowchart` exports (Field `discriminator="type"` renders as an explicit `oneOf`/`discriminator` block), which additionally gives the LLM structured-output constraint something concrete to follow when producing a node's type.

**Addendum (during `002`):** the field must not carry a Python-side default (`type: Literal["start"]`, not `= "start"`). A default makes Pydantic list the field as optional in the exported JSON schema, and local Ollama structured output (llama3.2) reliably omitted it once it saw that — which then fails discriminated-union matching (`union_tag_not_found`) before `Flowchart`'s own validators ever run, since Pydantic can't apply a Python default to select a union member. With no default, `type` is `required` in the schema and the model consistently emits it. This costs a little construction ergonomics (every direct `StartNode(...)` call must now pass `type=...` explicitly) in exchange for correctness on the path this field exists for.
